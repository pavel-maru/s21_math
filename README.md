# s21_math

> **Status:** 🟢 **Complete (v1.0.1, 2026-10-06).**
> Собственная реализация `<math.h>` на C11 с Shewchuk double-double,
> FMA-based range reduction и поддержкой трёх платформенных режимов.
> 454 теста, 100% покрытие, 10 задокументированных экспериментов.

Собственная реализация стандартной библиотеки `<math.h>` на языке C (C11).
Учебный проект Школы 21 (School 21 / École 42), развитый в пет-проект
с несколькими подходами к повышению точности вычислений и поддержкой
нескольких платформ.

## Платформы и разрядность long double

Проект написан с учётом того, что **размер `long double` различается
на разных платформах**:

| Платформа | `__LDBL_MANT_DIG__` | `long double` | Эпсилон | Точность |
|---|---|---|---|---|
| x86-64 Linux | 64 | 80 бит (extended) | ~1.08e-19 | высокая |
| ARM64 Linux | 113 | 128 бит (quad) | ~1.93e-34 | предельная |
| **ARM64 macOS** | **53** | **64 бита (`double`)** | **~2.22e-16** | **базовая** |
| x86-64 с `-mlong-double-64` | 53 | 64 бита (`double`) | ~2.22e-16 | базовая |

**Важно:** на Apple Silicon (M1/M2/M3) `long double` — это просто
`double`. ARM64 macOS не поддерживает 80-битный формат x87,
и Apple явно указывает, что для большей точности нужны сторонние
библиотеки, работающие программно.

Чтобы проект собирался и проходил тесты на всех платформах,
в `s21_math.c` разрядность определяется через `__LDBL_MANT_DIG__`
и под неё подбираются:

- порог сходимости `S21_EPS`,
- лимит итераций `S21_MAX_ITER`,
- граница переполнения `S21_EXP_LIMIT`,
- **константы 2π и ln 2 в виде пар `HI + LO`**.

Таблица параметров:

| Параметр | 53 (double) | 64 (80-bit) | 113 (quad) |
|---|---|---|---|
| `S21_EPS` | `1e-15L` | `1e-25L` | `1e-35L` |
| `S21_MAX_ITER` | `100` | `300` | `400` |
| `S21_EXP_LIMIT` | `709.0L` | `11356.0L` | `11356.0L` |
| `S21_2PI_HI` | `6.2831853071795862…` | `6.28318530717958648…` | `6.283185307179586476925…` |
| `S21_2PI_LO` | `+2.449e-16` | `−1.003e-19` | `+1.734e-34` |
| `S21_LN2_HI` | `0.6931471805599453…` | `0.693147180559945309…` | `0.693147180559945309417…` |
| `S21_LN2_LO` | `+2.319e-17` | `−1.146e-20` | `−7.008e-36` |

Значения `HI`/`LO` получены эмпирически probe-программами (см.
раздел [Структура проекта](#структура-проекта) → `materials/`).

В `test.c` допуск `EPS` также адаптируется: `1e-12` для 80/128-бит
и `1e-10` для 64-бит.

### ABI workaround для нестандартной разрядности на x86-64

При симуляции Apple Silicon на x86-64 (`-mlong-double-64`)
возникает ABI-проблема: **glibc собрана под 80-битный
`long double`**, а gcc при `-mlong-double-64` передаёт `long double`
через SSE-регистры (как `double`). Аналогичный эффект
при `-mlong-double-128`. Результат:

- `expl`, `logl`, `sinl`, `cosl`, `atanl` получают мусор
  и возвращают `nan`;
- `nextafterl` возвращает `-nan`;
- `printf("%Le", x)` читает из стека 16 байт вместо 8 и печатает
  мусор.

На реальном Apple Silicon этой проблемы нет — там libc
скомпилирована под 64-битный `long double`. Но для корректной
симуляции на Linux в `test.c` и `bench.c` введены макросы:

```c
#if defined(__LDBL_MANT_DIG__) && __LDBL_MANT_DIG__ == 53
  #define S21_NEXTAFTER(x, y) nextafter((double)(x), (double)(y))
  #define S21_LIBM_FN(name, x) ((long double)name((double)(x)))
  #define S21_PRINT_LD(x) printf("%-11.2e", (double)(x))
#else
  #define S21_NEXTAFTER(x, y) nextafterl((x), (y))
  #define S21_LIBM_FN(name, x) name##l(x)
  #define S21_PRINT_LD(x) printf("%-11.2Le", (x))
#endif
```

Аналогично в `s21_math.c` функция `s21_two_product` использует
`__builtin_fmal` в 80/128-битном режиме и `__builtin_fma`
(для `double`) в 64-битном.

## 128-битный long double

По умолчанию проект собирается с 80-битным `long double`
(x86 extended precision). Для экспериментов доступен режим
с **128-битным** `long double` (IEEE 754 quad precision):

```sh
make test-128     # прогон тестов в 128-битном режиме
make gcov-128     # покрытие в 128-битном режиме
make clean-128    # очистка после 128-битного прогона
```

Эквивалентно флагам:

```sh
make test LDBL=-mlong-double-128
make gcov_report LDBL=-mlong-double-128
```

### Что даёт 128-битный режим

- **Точность:** ~33 значащие цифры вместо ~18.
- **`exp`, `log`, `atan`, `sin`, `cos`:** отклонение от `libm`
  падает до нуля (0 ULP), включая `sin(1e10)` и `cos(1e10)`.
- **Совместимость:** работает только на x86/x86-64 (gcc).
  На ARM64 macOS `-mlong-double-128` не поддерживается.

### Известное ограничение: ABI libcheck

`libcheck` на типовых Linux-системах собран под 80-битный
`long double`. При прогоне тестов с `-mlong-double-128`:

- **таблицы ULP печатаются корректно** и показывают 0 везде
  (кроме шумовых денормализованных `3.36e-4932` — это артефакт
  `nextafterl` в libcheck, не относящийся к нашей библиотеке);
- **`ck_assert_ldouble_eq_tol` в конце `test_precision_compare`
  падает** с `SIGSEGV` — libcheck читает `long double` из стека
  как 80-битное значение, а получает 128-битное.

Итог на типовой Linux-системе: **450/454 checks (99%)**.
Прочие asserts (`test_fabs`, `test_ceil`, `test_sqrt`, `test_exp`,
`test_sin_loop`, `test_cos_loop`, `test_pow_loop`) проходят — там
libcheck не трогает `long double` напрямую.

Это **не ошибка библиотеки**. Точность самих функций
подтверждается таблицами ULP, которые печатаются нашим `printf`
в обход libcheck. Все значения — 0 ULP на всём диапазоне.

В 64-битном режиме на этой же системе libcheck, наоборот,
отрабатывает полностью (454/454) — видимо, его сборка
совместима с `double`-ABI для `long double`.

## Как устроено внутри

### Ключевые алгоритмы

| Функция | Подход |
|---|---|
| `sqrt` | метод Ньютона–Рафсона с масштабированием аргумента в `[0.25, 1]` |

| `log` | приведение к `[1,2)`, ряд `log((1+z)/(1−z))` |
| `pow` | для целых — точное бинарное возведение; для дробных — `exp(e·log(b))` |
| `sin`/`cos` | dd-based range reduction по модулю `2π`, ряд Тейлора |
| `tan` | `sin(x) / cos(x)` |
| `atan` | argument reduction + ряд Тейлора |
| `asin` | `atan(x / √(1−x²))` |
| `acos` | `π/2 − asin(x)` |
| `fmod` | пошаговое вычитание с удвоением |

### Вспомогательные хелперы

- `s21_isnan_l`, `s21_isinf_l` — детект NaN и INF.
- `s21_fabsl` — `|x|` для `long double`.
- `s21_signbit_l` — знак числа, включая знак нуля.
- `s21_trunc_l` — отбрасывание дробной части (до `2^64`).
- `s21_is_odd_int` — нечётное целое (для `pow(-0.0, …)`).
- `s21_ldexp_int` — умножение на `2^n` для любого целого `n`.
- `s21_reduce_2pi` — dd-based приведение аргумента по модулю `2π`.
- `s21_powi` — точное бинарное возведение в целую степень.
- `s21_ulp_diff` (в `test.c`) — ULP-разница с эталоном `libm`.

### Shewchuk double-double

Для повышения точности суммирования длинных рядов используется
**метод Шевчука** в форме расширения из 2 компонент (`s21_dd`):

```c
typedef struct {
  long double hi;
  long double lo;
} s21_dd;
```

Ключевые операции:

- `s21_two_sum(a, b, *s, *err)` — точное сложение двух чисел.
- `s21_two_product(a, b, *p, *err)` — точное произведение через FMA.
- `s21_dd_add(a, b)` — сложение двух dd-чисел с ре-нормализацией.
- `s21_dd_ldexp(a, n)` — точное умножение dd на `2^n`.
- `s21_dd_value(a)` — сборка dd в одно `long double`.

### DD-based range reduction для sin/cos

Ключевая оптимизация v9. Проблема: при приведении `x` по модулю
`2π` для больших `x` разность `x − n·2π` мала, но обе величины
имеют абсолютную ошибку `|x|·ε`. В 64-битном режиме (Apple Silicon)
это даёт `1e10·2.2e-16 ≈ 2e-6` в остатке `r`, что приводит к
ULP ~`1e9` на `sin(1e10)`.

Решение — выполнить вычитание в double-double:

```c
static long double s21_reduce_2pi(long double x) {
  long double n = s21_trunc_l(x / S21_2PI);

  /* n·2π_hi через two_product — точно */
  long double p_hi, p_err;
  s21_two_product(n, S21_2PI_HI, &p_hi, &p_err);
  long double p_lo = n * S21_2PI_LO;

  s21_dd n_2pi;
  s21_two_sum(p_hi, p_err + p_lo, &n_2pi.hi, &n_2pi.lo);

  /* r = x − n·2π в dd */
  s21_dd x_dd = s21_dd_make(x);
  s21_dd neg = {-n_2pi.hi, -n_2pi.lo};
  s21_dd r_dd = s21_dd_add(x_dd, neg);
  return s21_dd_value(r_dd);
}
```

Это снижает ошибку в `r` до `|x|·ε²`:
- 80-бит: `1e10·(1.08e-19)² ≈ 1e-28`
- 64-бит: `1e10·(2.22e-16)² ≈ 5e-22`

**Важно:** сам dd-механизм даёт выигрыш, только если константы
`S21_2PI_HI` и `S21_2PI_LO` **верны для текущей разрядности**
`long double`. До v10 они были прописаны под 64-битный `double`
и на 80/128-бит давали систематическую ошибку `n·|ΔLO|`, которая
сводила выигрыш dd к нулю. Начиная с v10 константы заданы
отдельно для каждой разрядности (см. таблицу в разделе
[Платформы](#платформы-и-разрядность-long-double)).

## Точность вычислений

- **Машинный эпсилон** `long double` (80 бит): ≈ 1.08e-19.
- **Машинный эпсилон** `long double` (128 бит): ≈ 1.93e-34.
- **Машинный эпсилон** `double` (64 бита): ≈ 2.22e-16.

- **Тесты проверяют**: `EPS = 1e-12` (80/128-бит) или `1e-10`

## Эволюция подхода к точности

### Проблема: ошибки округления при суммировании рядов

Все тригонометрические и показательные функции вычисляются через
разложение в ряд Тейлора. Слагаемые различаются на много порядков,
и младшие биты теряются при сложении. Это классическая **потеря
значимости** (loss of significance), ошибка накапливается как
`O(n·ε)`.

### v1: компенсационное суммирование по Кэхэну

Алгоритм Кэхэна снижает ошибку с `O(n·ε)` до `O(ε)`. Работает
за `O(1)` памяти, ~4 операции на сложение. Применялся во всех
функциях с рядами, сохранён в ветке `v1-kahan`.

### v2: метод Шевчука (double-double)

Идея: хранить не одно `long double`, а два — `hi` и `lo`, сумма
которых точно равна результату. Точность `O(ε²)`, независимость
от порядка суммирования. Метод назван в честь **Джонатана Шевчука**
(UC Berkeley), опубликовавшего работу в 1996 году. Используется
в `math.fsum()` в Python. Ветка `v2-shewchuk`.

### v3: 128-битный long double

Эксперимент с `-mlong-double-128`. Все функции начинают совпадать
с `libm` побитово (0 ULP), включая `sin(1e10)` и `cos(1e10)`.
Argument reduction problem исчезает — 33 значащих цифр хватает.
Ветка `v3-128bit-ldbl`.

### v4: FMA-based range reduction для exp

Range reduction `r = y − k·ln2` через FMA. В 80-битном режиме
дало 2–3× улучшение `exp`:

| x | Было | Стало |
|---|---|---|
| 5.0 | 2.78e-17 | 1.39e-17 |
| 10.0 | 7.11e-15 | 3.55e-15 |
| 20.0 | 2.62e-10 | 1.75e-10 |
| 100.0 | 1.38e+26 | 4.35e+25 |

Ветка `v4-exp-precision`.

### v5: FMA для sin/cos (неудачная гипотеза)

Попытка применить FMA к range reduction `sin`/`cos`. Улучшения
не последовало ни на малых, ни на больших аргументах. Узкое
место — накопление погрешности в ряде Тейлора, а не range
reduction. Негативный результат сохранён в ветке `v5-fma-trig`.

### v6: ULP-метрика

Дополнительно к абсолютным отклонениям добавлена ULP-метрика.
Позволяет сравнивать точность разных функций и видеть, где мы
находимся относительно предела представимости. Ветка
`v6-ulp-report`.

### v7: бенчмарк производительности

Замеры 10⁶ вызовов каждой функции с `-O2` против `libm`.
Ветка `v7-benchmark`, актуальные цифры — в разделе
[Бенчмарк производительности](#бенчмарк-производительности).

### v8: порт на ARM / Apple Silicon

При портировании выяснилось, что `long double` имеет разную
разрядность:

- x86-64 Linux — 80 бит
- ARM64 Linux — 128 бит (quad)
- **ARM64 macOS — 64 бита (`double`)**

Для поддержки всех платформ введён флаг `S21_LDBL_IS_DOUBLE`.
В 64-битном режиме параметры адаптируются под `double`.
Дополнительно добавлены ABI workaround'ы для симуляции
Apple Silicon на x86-64: `S21_LIBM_FN`, `S21_NEXTAFTER`,
`S21_PRINT_LD`. Ветка `v8-arm-port`.

### v9: dd-based range reduction для sin/cos

**Ключевое улучшение.** Раньше вычитание `r = x − n·2π`
выполнялось в `long double`, что давало ошибку `|x|·ε` в остатке.
В 64-битном режиме при `x = 1e10` это `2e-6`, что приводило к
ULP ~`1e9` на `sin(1e10)`.

Решение — вычислить `n·2π` через `s21_two_product` (точное
произведение через FMA) и вычесть через `s21_dd_add`. Ошибка
в остатке падает до `|x|·ε²`.

**Результаты в 64-битном режиме (Apple Silicon simulation):**

| Функция | Аргумент | ULP до v9 | ULP после v9 |
|---|---|---|---|
| `sin` | `1e6` | 5.63e+05 | **0** |
| `sin` | `1e10` | 3.67e+09 | **75** |
| `cos` | `1e6` | 1.05e+05 | **16** |
| `cos` | `1e10` | 1.02e+09 | **25** |

Улучшение на **7–8 порядков**. Argument reduction problem решён
**на всех платформах**, включая Apple Silicon с 64-битным
`long double`. Ветка `v9-dd-for-double`.

### v10: платформенные константы, краевые кейсы и чистый пересбор

При перепроверке точности на 80- и 128-битных платформах
обнаружилось, что `S21_2PI_HI/LO` и `S21_LN2_HI/LO` в v9 были
прописаны под 64-битный `long double`. На других разрядностях это
давало систематическую ошибку `n·|ΔLO|`, которая сводила выигрыш
dd-based range reduction к нулю: на 80-бит `sin(1e10)` показывал
~`1e13` ULP вместо ожидаемых десятков.

Дополнительно нашли и починили несколько независимых багов:

- `s21_ldexp_int` зацикливался при `n < 0` — не влияло на работу
  до v10, но всплыло при добавлении масштабирования в `sqrt`.
- `s21_trunc_l` через `long long` не работал для `|x| ≥ 2^63`,
  что ограничивало `reduce_2pi` диапазоном ~`5.8e19`. Расширили
  до `2^64` через `unsigned long long`.
- `s21_sqrt` не сходился за 100 итераций для `x < 1e-10`. Добавили
  масштабирование аргумента в `[0.25, 1]` с последующим `ldexp`.
- `abs(INT_MIN)`, `-0.0` в `ceil`/`floor`/`fmod`, `pow(-0.0, ±odd)`
  — стандартные краевые кейсы, не покрытые тестами.
- `s21_log`: `count·LN2_HI` без `two_product` терял младшие биты
  → 1 ULP на `1e6`. Стоимость `log` выросла примерно на 150%.
- `bench.c` не собирался в 64-битном режиме из-за ABI (аналогично
  `test.c`).
- **`Makefile`:** цели `test-128` и `test-64` не пересобирали
  `s21_math.a`, если менялся флаг `LDBL`. Линковка `test.c` с
  библиотекой от другой разрядности давала мусор и segfault в
  libcheck. Теперь `test` сам делает `clean` и пересобирает всё
  с нуля, поэтому переключение между режимами безопасно в любую
  сторону.

**Константы измерены probe-программами**, лежащими в `materials/`:

- `probe_consts2.c` — для 80- и 64-битного `long double`. Печатает
  `HI`, `LO` и остаток `true − HI` с использованием `__float128`
  для точной арифметики.
- `probe_128_mpfr.c` — для 128-битного quad. Использует **MPFR**
  с 256-битной точностью, потому что `__float128` совпадает по
  точности с quad и не может вычислить остаток.

**Результаты после v10 (80-бит):**

| Функция | Аргумент | ULP до v10 | ULP после v10 |
|---|---|---|---|
| `sin` | `1e6` | 1.28e+09 | **28** |
| `sin` | `1e10` | 1.19e+13 | **53** |
| `cos` | `1e6` | 2.38e+08 | **55** |
| `cos` | `1e10` | 3.32e+12 | **16** |

Ветка `v10-fix-constants`.

### Сравнение подходов

| Метод | Ошибка суммирования | Стоимость итерации | Память на число |
|---|---|---|---|
| Обычное сложение | `O(n·ε)` | 1 операция | 1 × `long double` |
| Кэхэн | `O(ε)` | ~4 операции | 2 × `long double` |
| Шевчук (dd) | `O(ε²)` | ~6 операций | 2 × `long double` |
| Шевчук + FMA | `O(ε²)` + точный range reduction | ~6 операций | 2 × `long double` |
| DD-based range reduction | `O(ε²)` на всех платформах | +2 two_product | 2 × `long double` |
| Платформенные константы (v10) | `O(ε²)` на 80/64/128-бит | без изменений | — |

### Итог

Проект проходит 454 из 454 тестов на:
- x86-64 Linux (80-бит) с точностью `1e-12` и ULP `≤ 55` на всём
  диапазоне, включая `sin(1e10)` и `cos(1e10)`.
- ARM64 macOS / Apple Silicon (64-бит) с точностью `1e-10` и
  ULP `≤ 75` на всём диапазоне, включая `sin(1e10)`.

В 128-битном режиме на x86-64 Linux проходит 450 из 454 checks:
падает только `test_precision_compare` из-за ABI `libcheck`.
Таблицы ULP при этом показывают 0 везде.

История коммитов: `v1-kahan` → `v2-shewchuk` → `v3-128bit-ldbl`
→ `v4-exp-precision` → `v5-fma-trig` → `v6-ulp-report`
→ `v7-benchmark` → `v8-arm-port` → `v9-dd-for-double`
→ `v10-fix-constants`.


Замеряет 10⁶ вызовов каждой функции с `-O2` и сравнивает с `libm`.

| Функция | s21 (ns/call) | libm (ns/call) | ratio |
|---|---|---|---|
| `fmod` | 16.0 | 12.1 | 1.32× |
| `sqrt` | 46.4 | 7.4 | 6.26× |
| `sin` | 265.0 | 158.0 | 1.68× |
| `cos` | 265.4 | 158.3 | 1.68× |
| `atan` | 324.0 | 56.4 | 5.74× |
| `asin` | 390.2 | 35.4 | 11.01× |
| `acos` | 392.6 | 71.6 | 5.49× |
| `log` | 468.4 | 33.1 | 14.15× |
| `tan` | 534.4 | 156.8 | 3.41× |
| `exp` | 692.9 | 72.6 | 9.55× |

Изменения относительно v1.0.0:

- `sqrt` подорожал на ~7% — плата за масштабирование аргумента

- `sin`, `cos`, `tan`, `asin`, `acos` — рост на 10–20% из-за

## Структурное программирование

Проект следует принципам Дейкстры:

- ✅ Нет `goto`.
- ✅ Только `if`, `while`, `for`, `return`.
- ✅ Вложенность блоков ≤ 4.
- ✅ Повторяющиеся фрагменты вынесены в `static`-функции.
- ✅ Нет глобальных переменных.
- ✅ Не более одного `break` на цикл.
- ✅ Размер функций ≤ 50 строк.
- ⚠️ Ранние `return` используются как проверки аргументов
  (разрешено исключением принципа 6).
