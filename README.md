Учебный проект Школы 21 (School 21 / École 42), развитый в пет-проект
с несколькими подходами к повышению точности вычислений.

## Платформы и разрядность long double

Проект написан с учётом того, что **размер `long double` различается
на разных платформах**:

| Платформа | `__LDBL_MANT_DIG__` | `long double` | Эпсилон | Точность |
|---|---|---|---|---|
| x86-64 Linux | 64 | 80 бит (extended) | ~1.08e-19 | высокая |
| ARM64 Linux | 113 | 128 бит (quad) | ~1.93e-34 | предельная |
| **ARM64 macOS** | **53** | **64 бита (`double`)** | **~2.22e-16** | **базовая** |
| x86-64 с `-mlong-double-64` | 53 | 64 бита (`double`) | ~2.22e-16 | базовая |

**Важно:** на Apple Silicon (M1/M2/M3) `long double` — это просто
`double`. ARM64 macOS не поддерживает 80-битный формат x87,
и Apple явно указывает, что для большей точности нужны сторонние
библиотеки, работающие программно.

Чтобы проект собирался и проходил тесты на всех платформах,
в `s21_math.c` введён флаг `S21_LDBL_IS_DOUBLE`, который
автоматически определяется через `__LDBL_MANT_DIG__ == 53`:

```c
#if defined(__LDBL_MANT_DIG__) && __LDBL_MANT_DIG__ == 53
  #define S21_LDBL_IS_DOUBLE 1
#else
  #define S21_LDBL_IS_DOUBLE 0
#endif
```

При `S21_LDBL_IS_DOUBLE == 1` параметры адаптируются под `double`:

| Параметр | 80/128-бит | 64-бит (`double`) |
|---|---|---|
| `S21_EPS` | `1e-25L` | `1e-15L` |
| `S21_MAX_ITER` | `300` | `100` |
| `S21_EXP_LIMIT` | `11356.0L` | `709.0L` (ln(DBL_MAX)) |

В `test.c` аналогично адаптируется допуск `EPS`: `1e-12` для
80/128-бит и `1e-10` для 64-бит.

**Что это показывает:** точность численных алгоритмов ограничена
платформой. Даже Shewchuk double-double и FMA-based range reduction
не могут преодолеть тот факт, что на Apple Silicon `long double`
имеет только 15–16 значащих цифр. Это фундаментальное ограничение,
а не баг реализации.

## 128-битный long double

По умолчанию проект собирается с 80-битным `long double`
(x86 extended precision). Для экспериментов доступен режим
с **128-битным** `long double` (IEEE 754 quad precision):

```sh
make test-128     # прогон тестов в 128-битном режиме
make gcov-128     # покрытие в 128-битном режиме
make clean-128    # очистка после 128-битного прогона
```

Эквивалентно флагам:

```sh
make test LDBL=-mlong-double-128
make gcov_report LDBL=-mlong-double-128
```

### Что даёт 128-битный режим

- **Точность:** ~33 значащие цифры вместо ~18.
- **`exp`, `log`, `atan`, `sin`, `cos`:** отклонение от `libm`
  падает до нуля (0 ULP).
- **Совместимость:** работает только на x86/x86-64 (gcc).
  На ARM64 macOS `-mlong-double-128` не поддерживается.
- **Совместимость с libcheck:** может конфликтовать. Если `libcheck`
  собран под 80-битный `long double`, сравнения в тестах могут падать
  на границах допуска.

### Когда стоит включать

- Проверка гипотезы «насколько точнее может быть?»
- Сравнение алгоритмов (Kahan vs Shewchuk) на предельной точности.
- Демонстрация на защите: «вот 80 бит, вот 128 бит, вот таблица
  отклонений».

Для повседневной сборки и сдачи достаточно 80-битного режима.

## Ветки

Проект развивался как серия экспериментов с разными подходами
к точности суммирования.

- **`main`** — финальная версия: Shewchuk double-double,
  FMA-based range reduction для `exp`, поддержка 80-, 128-
  и 64-битного `long double`, ULP-метрика, бенчмарк,
  454 checks, покрытие 100%.
- **`v1-kahan`** — первая версия: компенсационное суммирование
  по Кэхэну.
- **`v2-shewchuk`** — переход на double-double расширение
  по Шевчуку.
- **`v3-128bit-ldbl`** — эксперимент с 128-битным `long double`
  и удобными целями в `Makefile`.
- **`v4-exp-precision`** — FMA-based range reduction для `exp`
  в 80-битном режиме.
- **`v5-fma-trig`** — неудачная гипотеза: FMA для range
  reduction `sin`/`cos`.
- **`v6-ulp-report`** — ULP-метрика точности.
- **`v7-benchmark`** — бенчмарк производительности.
- **`v8-arm-port`** — адаптация под ARM64 и Apple Silicon,
  где `long double` == `double`.

## Как устроено внутри

### Ключевые алгоритмы

| Функция | Подход |
|---|---|
| `sqrt` | метод Ньютона–Рафсона, квадратичная сходимость |
| `exp` | разложение `y = k·ln2 + r`, FMA-based range reduction, ряд Тейлора, умножение на `2^k` |
| `log` | приведение к `[1,2)`, ряд `log((1+z)/(1-z)) = 2·(z + z³/3 + ...)`, где `z = (y-1)/(y+1)` |
| `pow` | для целых показателей — точное бинарное возведение; для дробных — `exp(e·log(b))` |
| `sin`/`cos` | range reduction по модулю `2π` (разбитая константа `HI+LO`), ряд Тейлора |
| `tan` | `sin(x) / cos(x)` |
| `atan` | `atan(x) = 2·atan(x / (1 + √(1+x²)))` + ряд Тейлора |
| `asin` | `atan(x / √(1-x²))` |
| `acos` | `π/2 − asin(x)` |
| `fmod` | пошаговое вычитание с удвоением — устойчиво к большим аргументам |

### Вспомогательные хелперы

- `s21_isnan_l`, `s21_isinf_l` — детект NaN и INF.
- `s21_fabsl` — `|x|` для `long double`.
- `s21_trunc_l` — отбрасывание дробной части.
- `s21_ldexp_int` — быстрое умножение на `2^n`.
- `s21_reduce_2pi` — приведение аргумента по модулю `2π`.
- `s21_powi` — точное бинарное возведение в целую степень.
- `s21_ulp_diff` (в `test.c`) — ULP-разница между результатом
  и эталоном `libm`.

### Shewchuk double-double

Для повышения точности суммирования длинных рядов используется
**метод Шевчука** в форме расширения из 2 компонент (`s21_dd`):

```c
typedef struct {
  long double hi;
  long double lo;
} s21_dd;
```

Ключевые операции:

- `s21_two_sum(a, b, *s, *err)` — точное сложение двух чисел:
  `s + err == a + b` (математически, а не по плавающей арифметике).
- `s21_dd_add(a, b)` — сложение двух dd-чисел с сохранением
  потерянных битов и ре-нормализацией.
- `s21_dd_ldexp(a, n)` — точное умножение dd на `2^n`.
- `s21_dd_value(a)` — сборка dd в одно `long double`.

Применяется в: `s21_exp`, `s21_log`, `s21_sin`, `s21_cos`, `s21_atan`.

### FMA-based range reduction для exp

В 80- и 64-битном режиме range reduction `r = y − k·ln2`
вычисляется через FMA (`__builtin_fmal`):

```c
long double khi = (long double)k * S21_LN2_HI;
long double khi_err = __builtin_fmal((long double)k, S21_LN2_HI, -khi);
```

Это даёт точное произведение `k·LN2_HI` в виде двух компонент
(`khi + khi_err`). Затем эти компоненты вычитаются из `y` через
`s21_dd_add` — младшие биты не теряются.

Guard `#if __LDBL_MANT_DIG__ == 113` отключает FMA-путь в
128-битном режиме: x87 не поддерживает FMA для quad precision,
`__builtin_fmal` там вызывает segfault. В 128-битном режиме
используется обычное разбитое вычитание — точности и так хватает.

## Точность вычислений

- **Машинный эпсилон** `long double` (80 бит): ≈ 1.08e-19.
- **Машинный эпсилон** `long double` (128 бит): ≈ 1.93e-34.
- **Машинный эпсилон** `double` (64 бита): ≈ 2.22e-16.
- **Требование задания**: 16 значащих цифр, 6 знаков после запятой.
- **Тесты проверяют**: `EPS = 1e-12` (80/128-бит) или `1e-10`
  (64-бит).

Точность достигнута за счёт:

1. Разбитых констант (`2π_hi + 2π_lo`, `ln2_hi + ln2_lo`) для
   range reduction.
2. Shewchuk double-double для суммирования рядов.
3. Точного бинарного возведения для целых степеней (`s21_powi`).
4. Устойчивого `fmod` для больших аргументов.
5. FMA-based range reduction для `exp` (80- и 64-битный режим).

на больших аргументах, ULP-число растёт даже при хорошей
реализации.

### Платформенные различия

**На Apple Silicon** (`long double == double`) точность падает
до уровня `double`: ~15–16 значащих цифр вместо ~19.
Это отражается в:

- `S21_EPS = 1e-15L` вместо `1e-25L`
- `S21_EXP_LIMIT = 709.0L` вместо `11356.0L` (`ln(DBL_MAX)`)
- допуск в тестах `EPS = 1e-10` вместо `1e-12`

Это **не деградация алгоритма**, а ограничение платформы.
Shewchuk dd и FMA-путь по-прежнему работают, но эффективный
эпсилон определяется размером `long double`, а не нашими
ухищрениями.

## Эволюция подхода к точности

*(раздел без изменений — см. предыдущие коммиты)*

### Седьмая версия: порт на ARM / Apple Silicon

При портировании проекта на ARM выяснилось, что `long double`
имеет **разную разрядность на разных платформах**:

- x86-64 Linux — 80 бит (extended precision)
- ARM64 Linux — 128 бит (quad, программная эмуляция)
- **ARM64 macOS (Apple Silicon) — 64 бита (просто `double`)**

На Apple Silicon `long double` не может хранить больше значащих
цифр, чем `double`. Это означает, что порог сходимости `S21_EPS`
в `1e-25L` **недостижим в принципе** — эпсилон `double` ~2.2e-16.

Для поддержки всех платформ введён флаг `S21_LDBL_IS_DOUBLE`,
автоматически определяемый через `__LDBL_MANT_DIG__ == 53`.
При этом:

- `S21_EPS` адаптируется (`1e-15L` для double)
- `S21_EXP_LIMIT` адаптируется (`709.0L = ln(DBL_MAX)`)
- `S21_MAX_ITER` уменьшается (`100` вместо `300`)
- допуск в тестах — `1e-10` вместо `1e-12`

**Что это показывает:** даже точные численные алгоритмы
ограничены платформой. На Apple Silicon наш код становится
не хуже и не лучше `libm` — он работает в тех же 15–16 значащих
цифрах. Это фундаментальное ограничение, а не баг реализации.

### Итог

Проект проходит все 454 теста на:
- x86-64 Linux (80-бит) с точностью `1e-12`
- x86-64 Linux (128-бит) с точностью `1e-12` и 0 ULP

Цель `bench` собирает бинарник с `-O2`, прогоняет 10⁶ вызовов
каждой функции и сравнивает с `libm`.

Пример вывода (Intel, Ubuntu, gcc 13):

```
fn         s21 (ns/call)   libm (ns/call)      ratio
exp              683.93          72.83       9.39x
log              188.91          32.89       5.74x
sqrt              43.18           9.73       4.44x
sin              228.24         158.20       1.44x
cos              225.21         159.86       1.41x
tan              447.37         155.58       2.88x
atan             295.46          56.50       5.23x
asin             357.17          34.31      10.41x
acos             359.76          71.21       5.05x
pow              858.84         324.85       2.64x
fmod              12.89          18.91       0.68x
```

**Что важно:**

- `s21_*` в **0.7–10 раз** отличается от libm по скорости.
- **`fmod` быстрее libm** — простой цикл вычитания эффективнее
  glibc на малых аргументах.
- **`sin`/`cos` близки к libm** (1.4×).
- **`exp` медленнее в 9.4×** — цена dd + FMA + ряда Тейлора.
- **`asin` медленнее в 10.4×** — `atan` + `sqrt` внутри.

В 128-битном режиме производительность падает ещё в 3–5 раз:
quad precision эмулируется программно.
