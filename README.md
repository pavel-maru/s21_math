# s21_math

Собственная реализация стандартной библиотеки `<math.h>` на языке C (C11).
Учебный проект Школы 21 (School 21 / École 42), развитый в пет-проект
с несколькими подходами к повышению точности вычислений и поддержкой
нескольких платформ.

## Что реализовано

15 функций из `math.h` с префиксом `s21_`:

| Функция | Описание |
|---|---|
| `s21_abs(int x)` | абсолютное значение целого |
| `s21_fabs(double x)` | абсолютное значение с плавающей точкой |
| `s21_ceil(double x)` | округление вверх |
| `s21_floor(double x)` | округление вниз |
| `s21_fmod(double x, double y)` | остаток от деления |
| `s21_sqrt(double x)` | квадратный корень |
| `s21_exp(double x)` | экспонента `e^x` |
| `s21_log(double x)` | натуральный логарифм |
| `s21_pow(double base, double exp_val)` | возведение в степень |
| `s21_sin(double x)` | синус |
| `s21_cos(double x)` | косинус |
| `s21_tan(double x)` | тангенс |
| `s21_atan(double x)` | арктангенс |
| `s21_asin(double x)` | арксинус |
| `s21_acos(double x)` | арккосинус |

Все функции возвращают `long double` (кроме `s21_abs`), работают в радианах.

## Платформы и разрядность long double

Проект написан с учётом того, что **размер `long double` различается
на разных платформах**:

| Платформа | `__LDBL_MANT_DIG__` | `long double` | Эпсилон | Точность |
|---|---|---|---|---|
| x86-64 Linux | 64 | 80 бит (extended) | ~1.08e-19 | высокая |
| ARM64 Linux | 113 | 128 бит (quad) | ~1.93e-34 | предельная |
| **ARM64 macOS** | **53** | **64 бита (`double`)** | **~2.22e-16** | **базовая** |
| x86-64 с `-mlong-double-64` | 53 | 64 бита (`double`) | ~2.22e-16 | базовая |

**Важно:** на Apple Silicon (M1/M2/M3) `long double` — это просто
`double`. ARM64 macOS не поддерживает 80-битный формат x87,
и Apple явно указывает, что для большей точности нужны сторонние
библиотеки, работающие программно.

Чтобы проект собирался и проходил тесты на всех платформах,
в `s21_math.c` введён флаг `S21_LDBL_IS_DOUBLE`, который
автоматически определяется через `__LDBL_MANT_DIG__ == 53`:

```c
#if defined(__LDBL_MANT_DIG__) && __LDBL_MANT_DIG__ == 53
#define S21_LDBL_IS_DOUBLE 1
#else
#define S21_LDBL_IS_DOUBLE 0
#endif
```

При `S21_LDBL_IS_DOUBLE == 1` параметры адаптируются под `double`:

| Параметр | 80/128-бит | 64-бит (`double`) |
|---|---|---|
| `S21_EPS` | `1e-25L` | `1e-15L` |
| `S21_MAX_ITER` | `300` | `100` |
| `S21_EXP_LIMIT` | `11356.0L` | `709.0L` (ln(DBL_MAX)) |

В `test.c` аналогично адаптируется допуск `EPS`: `1e-12` для
80/128-бит и `1e-10` для 64-бит.

### ABI workaround для `-mlong-double-64` на x86-64

Помимо параметров, при симуляции Apple Silicon на x86-64
(`-mlong-double-64`) возникает ABI-проблема: **glibc скомпилирована
под 80-битный `long double`**, а gcc при `-mlong-double-64`
передаёт `long double` через SSE-регистры (как `double`). Результат:

- `expl`, `logl`, `sinl`, `cosl`, `atanl` получают мусор
  и возвращают `nan`;
- `nextafterl` возвращает `-nan`;
- `printf("%Le", x)` читает из стека 16 байт вместо 8 и печатает
  мусор.

На реальном Apple Silicon этой проблемы нет — там libc
скомпилирована под 64-битный `long double`. Но для корректной
симуляции на Linux в `test.c` введены три макроса:

```c
#if defined(__LDBL_MANT_DIG__) && __LDBL_MANT_DIG__ == 53
  #define S21_NEXTAFTER(x, y) nextafter((double)(x), (double)(y))
  #define S21_LIBM_FN(name, x) ((long double)name((double)(x)))
  #define S21_PRINT_LD(x) printf("%-11.2e", (double)(x))
#else
  #define S21_NEXTAFTER(x, y) nextafterl((x), (y))
  #define S21_LIBM_FN(name, x) name##l(x)
  #define S21_PRINT_LD(x) printf("%-11.2Le", (x))
#endif
```

- `S21_LIBM_FN(exp, x)` → `expl(x)` в 80/128-бит,
  `(long double)exp((double)x)` в 64-бит.
- `S21_NEXTAFTER` аналогично выбирает `nextafterl` или `nextafter`.
- `S21_PRINT_LD` печатает через `%Le` или `%e`.

Благодаря этим макросам тесты и таблицы точности корректно
работают во всех трёх режимах.

## 128-битный long double

По умолчанию проект собирается с 80-битным `long double`
(x86 extended precision). Для экспериментов доступен режим
с **128-битным** `long double` (IEEE 754 quad precision):

```sh
make test-128     # прогон тестов в 128-битном режиме
make gcov-128     # покрытие в 128-битном режиме
make clean-128    # очистка после 128-битного прогона
```

Эквивалентно флагам:

```sh
make test LDBL=-mlong-double-128
make gcov_report LDBL=-mlong-double-128
```

### Что даёт 128-битный режим

- **Точность:** ~33 значащие цифры вместо ~18.
- **`exp`, `log`, `atan`, `sin`, `cos`:** отклонение от `libm`
  падает до нуля (0 ULP), включая `sin(1e10)` и `cos(1e10)`.
- **Совместимость:** работает только на x86/x86-64 (gcc).
  На ARM64 macOS `-mlong-double-128` не поддерживается.
- **Совместимость с libcheck:** может конфликтовать. Если `libcheck`
  собран под 80-битный `long double`, сравнения в тестах могут падать
  на границах допуска.

### Когда стоит включать

- Проверка гипотезы «насколько точнее может быть?»
- Сравнение алгоритмов (Kahan vs Shewchuk) на предельной точности.
- Демонстрация на защите: «вот 80 бит, вот 128 бит, вот таблица
  отклонений».

Для повседневной сборки и сдачи достаточно 80-битного режима.

## Ветки

Проект развивался как серия экспериментов с разными подходами
к точности суммирования.

- **`main`** — финальная версия: Shewchuk double-double,
  FMA-based range reduction для `exp`, поддержка 80-, 128-
  и 64-битного `long double`, ULP-метрика, бенчмарк,
  454 checks, покрытие 100%.
- **`v1-kahan`** — первая версия: компенсационное суммирование
  по Кэхэну.
- **`v2-shewchuk`** — переход на double-double расширение
  по Шевчуку.
- **`v3-128bit-ldbl`** — эксперимент с 128-битным `long double`.
- **`v4-exp-precision`** — FMA-based range reduction для `exp`
  в 80-битном режиме.
- **`v5-fma-trig`** — неудачная гипотеза: FMA для range
  reduction `sin`/`cos`.
- **`v6-ulp-report`** — ULP-метрика точности.
- **`v7-benchmark`** — бенчмарк производительности.
- **`v8-arm-port`** — адаптация под ARM64 и Apple Silicon,
  где `long double == double`.

## Как устроено внутри

### Ключевые алгоритмы

| Функция | Подход |
|---|---|
| `sqrt` | метод Ньютона–Рафсона, квадратичная сходимость |
| `exp` | разложение `y = k·ln2 + r`, FMA-based range reduction, ряд Тейлора, умножение на `2^k` |
| `log` | приведение к `[1,2)`, ряд `log((1+z)/(1-z)) = 2·(z + z³/3 + ...)`, где `z = (y-1)/(y+1)` |
| `pow` | для целых показателей — точное бинарное возведение; для дробных — `exp(e·log(b))` |
| `sin`/`cos` | range reduction по модулю `2π` (разбитая константа `HI+LO`), ряд Тейлора |
| `tan` | `sin(x) / cos(x)` |
| `atan` | `atan(x) = 2·atan(x / (1 + √(1+x²)))` + ряд Тейлора |
| `asin` | `atan(x / √(1-x²))` |
| `acos` | `π/2 − asin(x)` |
| `fmod` | пошаговое вычитание с удвоением — устойчиво к большим аргументам |

### Вспомогательные хелперы

- `s21_isnan_l`, `s21_isinf_l` — детект NaN и INF.
- `s21_fabsl` — `|x|` для `long double`.
- `s21_trunc_l` — отбрасывание дробной части.
- `s21_ldexp_int` — быстрое умножение на `2^n`.
- `s21_reduce_2pi` — приведение аргумента по модулю `2π`.
- `s21_powi` — точное бинарное возведение в целую степень.
- `s21_ulp_diff` (в `test.c`) — ULP-разница между результатом
  и эталоном `libm`.

### Shewchuk double-double

Для повышения точности суммирования длинных рядов используется
**метод Шевчука** в форме расширения из 2 компонент (`s21_dd`):

```c
typedef struct {
  long double hi;
  long double lo;
} s21_dd;
```

Ключевые операции:

- `s21_two_sum(a, b, *s, *err)` — точное сложение двух чисел:
  `s + err == a + b` (математически, а не по плавающей арифметике).
- `s21_dd_add(a, b)` — сложение двух dd-чисел с сохранением
  потерянных битов и ре-нормализацией.
- `s21_dd_ldexp(a, n)` — точное умножение dd на `2^n`.
- `s21_dd_value(a)` — сборка dd в одно `long double`.

Применяется в: `s21_exp`, `s21_log`, `s21_sin`, `s21_cos`, `s21_atan`.

### FMA-based range reduction для exp

Range reduction `r = y − k·ln2` вычисляется через FMA
(`__builtin_fmal`), но **только в 80-битном режиме**:

```c
#if defined(__LDBL_MANT_DIG__) && __LDBL_MANT_DIG__ == 64
  long double khi = (long double)k * S21_LN2_HI;
  long double khi_err = __builtin_fmal((long double)k, S21_LN2_HI, -khi);
  /* ... вычитание через dd_add ... */
#else
  r = y - k * S21_LN2_HI - k * S21_LN2_LO;
#endif
```

Это даёт точное произведение `k·LN2_HI` в виде двух компонент
(`khi + khi_err`). Затем эти компоненты вычитаются из `y` через
`s21_dd_add` — младшие биты не теряются.

**Почему FMA включается только для 80-битного формата:**

- **128-бит (quad, ARM64 Linux):** x87 FMA не поддерживает quad
  precision, `__builtin_fmal` вызывает segfault.
- **64-бит (Apple Silicon, `-mlong-double-64`):** `fmal` из libm
  ожидает 80-битный ABI, но получает 64-битный `long double`
  — несовпадение приводит к segfault.
- **80-бит (x86 extended):** единственный формат, где
  `__builtin_fmal` работает корректно.

Для 64- и 128-битного форматов используется обычное разбитое
вычитание — точности и так хватает.

## Точность вычислений

- **Машинный эпсилон** `long double` (80 бит): ≈ 1.08e-19.
- **Машинный эпсилон** `long double` (128 бит): ≈ 1.93e-34.
- **Машинный эпсилон** `double` (64 бита): ≈ 2.22e-16.
- **Требование задания**: 16 значащих цифр, 6 знаков после запятой.
- **Тесты проверяют**: `EPS = 1e-12` (80/128-бит) или `1e-10`
  (64-бит).

Точность достигнута за счёт:

1. Разбитых констант (`2π_hi + 2π_lo`, `ln2_hi + ln2_lo`) для
   range reduction.
2. Shewchuk double-double для суммирования рядов.
3. Точного бинарного возведения для целых степеней (`s21_powi`).
4. Устойчивого `fmod` для больших аргументов.
5. FMA-based range reduction для `exp` (80-битный режим).

- **0** — побитовое совпадение с `libm`.
- **1** — расхождение на одно представимое число `long double`.
- **N** — расхождение на N представимых чисел.

реализации.

- `sin`/`cos` — **1–40 ULP** до `1e3`, но на `1e6` и `1e10`
  argument reduction problem съедает всё: `5e5` и `1e9` ULP.
  Это фундаментальное ограничение `double`, а не нашего кода.
- **Все 454 теста проходят** с допуском `EPS = 1e-10` — то есть
  наши результаты укладываются в 10⁻¹⁰ даже там, где ULP большие.

Это **не деградация алгоритма**, а ограничение платформы.
Shewchuk dd и FMA-путь по-прежнему работают, но эффективный
эпсилон определяется размером `long double`, а не нашими
ухищрениями.

## Эволюция подхода к точности

Этот раздел описывает, как менялся механизм суммирования в процессе
разработки и почему финальный выбор пал на метод Шевчука.

### Проблема: ошибки округления при суммировании рядов

Все тригонометрические, показательные и логарифмические функции
вычисляются через разложение в ряд Тейлора. Ряд для `exp`, `sin`,
`cos`, `log`, `atan` содержит от 20 до 60 слагаемых, различающихся
по величине на несколько порядков. Когда очередное слагаемое
становится на 15–20 порядков меньше суммы, его младшие биты
«уезжают» за пределы мантиссы `long double` и теряются безвозвратно.

Это классическая **потеря значимости** (loss of significance).
Ошибка накапливается как `O(n·ε)`, где `n` — число слагаемых,
`ε` — машинный эпсилон.

### Первая версия: компенсационное суммирование по Кэхэну

Изначально применялся **алгоритм Кэхэна** (Kahan summation).
Идея: ввести дополнительную переменную `c` — компенсацию,
хранящую «хвост» от предыдущего сложения.

Реализация в виде макроса:

```c
#define S21_KAHAN_ADD(sum, c, term) \
  do {                              \
    long double _y = (term) - (c);  \
    long double _t = (sum) + _y;    \
    (c) = (_t - (sum)) - _y;        \
    (sum) = _t;                     \
  } while (0)
```

Снижает ошибку суммирования с `O(n·ε)` до `O(ε)`, работает за
`O(1)` дополнительной памяти. Промежуточная версия содержала
`S21_KAHAN_ADD` в `s21_math.c`. Сохранена в ветке `v1-kahan`.

### Вторая версия: метод Шевчука (double-double)

Вместо одного числа `long double` храним **два** — `hi` и `lo`,
сумма которых математически точно равна результату:

```c
typedef struct {
  long double hi;
  long double lo;
} s21_dd;
```

Ключевые операции: `s21_two_sum` (алгоритм 2Sum), `s21_dd_add`
с ре-нормализацией, `s21_dd_ldexp` (точное умножение на `2^n`),
`s21_dd_value` (сборка). Точность `O(ε²)` вместо `O(ε)`,
независимость от порядка суммирования.

Метод назван в честь **Джонатана Шевчука** (Jonathan Richard
Shewchuk, UC Berkeley), опубликовавшего работу *«Adaptive
Precision Floating-Point Arithmetic and Fast Robust Geometric
Predicates»* в 1996 году. Используется в `math.fsum()` в Python.

Ветка: `v2-shewchuk`.

### Третья версия: 128-битный long double

Эксперимент с `-mlong-double-128`. Все функции начинают совпадать
с `libm` побитово (0 ULP), включая `sin(1e10)` и `cos(1e10)`.

Причина: 33 значащих цифр хватает, чтобы `n = x/(2π)` не теряло
точность при извлечении остатка `r`. Argument reduction problem
полностью исчезает.

Ветка: `v3-128bit-ldbl`.

### Четвёртая версия: FMA-based range reduction для exp

Range reduction `r = y − k·ln2` через FMA. В 80-битном режиме
это дало 2–3-кратное улучшение:

| x | Было | Стало |
|---|---|---|
| 5.0 | 2.78e-17 | 1.39e-17 |
| 10.0 | 7.11e-15 | 3.55e-15 |
| 20.0 | 2.62e-10 | 1.75e-10 |
| 100.0 | 1.38e+26 | 4.35e+25 |

В 64- и 128-битном режимах FMA отключена — там она либо
не поддерживается (quad), либо даёт ABI mismatch (64-бит
с glibc).

Ветка: `v4-exp-precision`.

### Пятая версия: FMA для sin/cos (неудачная гипотеза)

Попытка применить FMA к range reduction `sin`/`cos` по модулю `2π`.
Улучшения не последовало ни на малых, ни на больших аргументах.

**Причина:** узкое место в `sin`/`cos` — не range reduction,
а накопление погрешности при вычислении слагаемых ряда Тейлора.
FMA улучшает только последний шаг, но не влияет на уже
накопленную погрешность.

Негативный результат сохранён в ветке `v5-fma-trig` для истории.

### Шестая версия: ULP-метрика

Дополнительно к абсолютным отклонениям добавлена **ULP-метрика** —
нормированная оценка точности в единицах младшего разряда.
Позволяет сравнивать точность разных функций между собой
и понимать, где мы находимся относительно предела представимости.

Реализация — хелпер `s21_ulp_diff` в `test.c`.

Ветка: `v6-ulp-report`.

| `fmod` | 12.89 | 18.91 | **0.68×** (быстрее) |
| `sin` | 228.24 | 158.20 | 1.44× |

### Восьмая версия: порт на ARM / Apple Silicon

При портировании проекта на ARM выяснилось, что `long double`
имеет **разную разрядность на разных платформах**:

- x86-64 Linux — 80 бит (extended precision)
- ARM64 Linux — 128 бит (quad, программная эмуляция)
- **ARM64 macOS (Apple Silicon) — 64 бита (просто `double`)**

Для поддержки всех платформ введён флаг `S21_LDBL_IS_DOUBLE`,
автоматически определяемый через `__LDBL_MANT_DIG__ == 53`.
Параметры `S21_EPS`, `S21_EXP_LIMIT`, `S21_MAX_ITER` адаптируются
под `double`.

FMA-based range reduction для `exp` включается **только**
при `__LDBL_MANT_DIG__ == 64` (80-бит). Для 64- и 128-битного
форматов используется обычное разбитое вычитание.

Дополнительно для симуляции Apple Silicon на x86-64
(`-mlong-double-64`) в `test.c` введены ABI workaround'ы:
`S21_LIBM_FN`, `S21_NEXTAFTER`, `S21_PRINT_LD`.

**Что показал эксперимент:** на Apple Silicon наш код работает
в тех же 15–16 значащих цифрах, что и `libm`. Это
**фундаментальное ограничение платформы**, а не деградация
алгоритма.

Ветка: `v8-arm-port`.

### Сравнение подходов

| Метод | Ошибка суммирования | Стоимость итерации | Память на число |
|---|---|---|---|
| Обычное сложение | `O(n·ε)` | 1 операция | 1 × `long double` |
| Кэхэн | `O(ε)` | ~4 операции | 2 × `long double` |
| Шевчук (dd) | `O(ε²)` | ~6 операций | 2 × `long double` |
| Шевчук + FMA (exp) | `O(ε²)` + точный range reduction | ~6 операций | 2 × `long double` |

### Итог

Проект проходит все 454 теста на:
- x86-64 Linux (80-бит) с точностью `1e-12`
- x86-64 Linux (128-бит) с точностью `1e-12` и 0 ULP
- ARM64 macOS / Apple Silicon (64-бит) с точностью `1e-10`

История коммитов: `v1-kahan` → `v2-shewchuk` → `v3-128bit-ldbl`
→ `v4-exp-precision` → `v5-fma-trig` → `v6-ulp-report`
→ `v7-benchmark` → `v8-arm-port`.
