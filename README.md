## 128-битный long double

По умолчанию проект собирается с 80-битным `long double`
(x86 extended precision, эпсилон ≈ 1.08e-19). Это стандарт для gcc
на x86-64 и полностью покрывает требования задания (16 значащих цифр).

Для экспериментов доступен режим с **128-битным** `long double`
(IEEE 754 quad precision, эпсилон ≈ 1.93e-34):

```sh
make test-128     # прогон тестов в 128-битном режиме
make gcov-128     # покрытие в 128-битном режиме
make clean-128    # очистка после 128-битного прогона
```

Эквивалентно флагам:

```sh
make test LDBL=-mlong-double-128
make gcov_report LDBL=-mlong-double-128
```

### Что даёт 128-битный режим

- **Точность:** ~33 значащие цифры вместо ~18.
- **`exp`, `log`, `atan`, `sin`, `cos`:** отклонение от `libm`
  падает до нуля или до машинного эпсилон `1e-34`.
- **Совместимость:** работает только на x86/x86-64 (gcc).
  На ARM и Apple Silicon `-mlong-double-128` не поддерживается.
- **Совместимость с libcheck:** может конфликтовать. Если `libcheck`
  собран под 80-битный `long double` (а это так в большинстве
  репозиториев Debian/Ubuntu), сравнения в тестах могут падать
  на границах допуска. В этом случае используй обычный режим.

### Когда стоит включать

- Проверка гипотезы «насколько точнее может быть?»
- Сравнение алгоритмов (Kahan vs Shewchuk) на предельной точности.
- Демонстрация на защите: «вот 80 бит, вот 128 бит, вот таблица
  отклонений».

Для повседневной сборки и сдачи достаточно 80-битного режима.

## Ветки

Проект развивался как серия экспериментов с разными подходами
к точности суммирования.

- **`main`** — финальная версия: Shewchuk double-double,
  FMA-based range reduction для `exp`, поддержка 80- и 128-битного
  режимов, ULP-метрика, 454 checks, покрытие 100%.
- **`v1-kahan`** — первая версия: компенсационное суммирование
  по Кэхэну. Показывает точку старта.
- **`v2-shewchuk`** — переход на double-double расширение
  по Шевчуку.
- **`v3-128bit-ldbl`** — эксперимент с 128-битным `long double`
  и удобными целями в `Makefile`.
- **`v4-exp-precision`** — FMA-based range reduction для `exp`
  в 80-битном режиме.
- **`v5-fma-trig`** — неудачная гипотеза: FMA для range
  reduction `sin`/`cos`. Улучшения нет ни на малых, ни на больших
  аргументах, ветка сохранена как архив негативного результата.
- **`v6-ulp-report`** — ULP-метрика точности в дополнение
  к абсолютным отклонениям.

## Как устроено внутри

### Ключевые алгоритмы

| Функция | Подход |
|---|---|
| `sqrt` | метод Ньютона–Рафсона, квадратичная сходимость |
| `exp` | разложение `y = k·ln2 + r`, FMA-based range reduction, ряд Тейлора, умножение на `2^k` |
| `log` | приведение к `[1,2)`, ряд `log((1+z)/(1-z)) = 2·(z + z³/3 + ...)`, где `z = (y-1)/(y+1)` |
| `pow` | для целых показателей — точное бинарное возведение; для дробных — `exp(e·log(b))` |
| `sin`/`cos` | range reduction по модулю `2π` (разбитая константа `HI+LO`), ряд Тейлора |
| `tan` | `sin(x) / cos(x)` |
| `atan` | `atan(x) = 2·atan(x / (1 + √(1+x²)))` + ряд Тейлора |
| `asin` | `atan(x / √(1-x²))` |
| `acos` | `π/2 − asin(x)` |
| `fmod` | пошаговое вычитание с удвоением — устойчиво к большим аргументам |

### Вспомогательные хелперы

- `s21_isnan_l`, `s21_isinf_l` — детект NaN и INF.
- `s21_fabsl` — `|x|` для `long double`.
- `s21_trunc_l` — отбрасывание дробной части.
- `s21_ldexp_int` — быстрое умножение на `2^n`.
- `s21_reduce_2pi` — приведение аргумента по модулю `2π`.
- `s21_powi` — точное бинарное возведение в целую степень.
- `s21_ulp_diff` (в `test.c`) — ULP-разница между результатом
  и эталоном `libm`.

### Shewchuk double-double

Для повышения точности суммирования длинных рядов используется
**метод Шевчука** в форме расширения из 2 компонент (`s21_dd`):

```c
typedef struct {
  long double hi;
  long double lo;
} s21_dd;
```

Ключевые операции:

- `s21_two_sum(a, b, *s, *err)` — точное сложение двух чисел:
  `s + err == a + b` (математически, а не по плавающей арифметике).
- `s21_dd_add(a, b)` — сложение двух dd-чисел с сохранением
  потерянных битов и ре-нормализацией.
- `s21_dd_ldexp(a, n)` — точное умножение dd на `2^n`.
- `s21_dd_value(a)` — сборка dd в одно `long double`.

Применяется в: `s21_exp`, `s21_log`, `s21_sin`, `s21_cos`, `s21_atan`.

### FMA-based range reduction для exp

В 80-битном режиме range reduction `r = y − k·ln2` вычисляется
через FMA (`__builtin_fmal`):

```c
long double khi = (long double)k * S21_LN2_HI;
long double khi_err = __builtin_fmal((long double)k, S21_LN2_HI, -khi);
```

Это даёт точное произведение `k·LN2_HI` в виде двух компонент
(`khi + khi_err`). Затем эти компоненты вычитаются из `y` через
`s21_dd_add` — младшие биты не теряются.

Guard `#if __LDBL_MANT_DIG__ == 113` отключает FMA-путь в
128-битном режиме: x87 не поддерживает FMA для quad precision,
`__builtin_fmal` там вызывает segfault. В 128-битном режиме
используется обычное разбитое вычитание — точности и так хватает.

## Точность вычислений

- **Машинный эпсилон** `long double` (80 бит): ≈ 1.08e-19.
- **Машинный эпсилон** `long double` (128 бит): ≈ 1.93e-34.
- **Требование задания**: 16 значащих цифр, 6 знаков после запятой.
- **Тесты проверяют**: `EPS = 1e-12` — на 7 порядков выше требуемого.

Точность достигнута за счёт:

1. Разбитых констант (`2π_hi + 2π_lo`, `ln2_hi + ln2_lo`) для
   range reduction.
2. Shewchuk double-double для суммирования рядов.
3. Точного бинарного возведения для целых степеней (`s21_powi`).
4. Устойчивого `fmod` для больших аргументов.
5. FMA-based range reduction для `exp` (80-битный режим).

### ULP-метрика

`make test` дополнительно печатает таблицу отклонений в **ULP**
(units in the last place) — нормированную метрику:

- **0** — побитовое совпадение с `libm`.
- **1** — расхождение на одно представимое число `long double`.
- **N** — расхождение на N представимых чисел.

Формула:

```
ULP(got, expected) = |got - expected| / ulp(expected)
ulp(x) = nextafterl(x, +inf) - x
```


**Как читать:**

- **`log`** — 0–1 ULP везде. Double-double + разбитый `ln2`
  дают эталонную точность.
- **`exp`** — 0–2 ULP на малых аргументах, растёт до 247 ULP
  на `x = 1000`. Это ожидаемо: `exp` растёт экспоненциально,
  и ошибка `r` в range reduction умножается на `e^1000`.
  **Относительная** точность при этом остаётся на уровне `ε`.
- **`atan`** — 200–350 ULP на малых `x` при абсолютной ошибке
  ~`1e-17`. Это не баг: `atan(0.5) ≈ 0.46`, ULP ≈ `5e-20`,
  и мы уже на пределе точности `long double`. Абсолютное отклонение
  здесь — лучшая метрика, чем ULP.
- **`sin`/`cos`** — растёт до `1e13 ULP` на `x = 1e10`. Это
  **argument reduction problem**: `libm` тоже неточна на таких
  аргументах, и мы видим разницу двух неточностей. Подробнее —
  в разделе про `v5-fma-trig`.

**Все функции — 0 ULP во всём диапазоне.** `3.36e-4932`
для `log` — это минимальное денормализованное `long double`,
то есть фактически машинный ноль. Побитовое совпадение с `libm`.

Особенно важно, что **`sin(1e10)` и `cos(1e10)` в 128-битном
режиме дают 0 ULP**, тогда как в 80-битном — `1e13 ULP`. Это
прямое доказательство, что argument reduction problem решается
переходом на quad precision: 33 значащие цифры хватает, чтобы
`n = x/(2π)` не теряло точность при извлечении остатка `r`.

**Важно:** ULP-метрика показывает расхождение с `libm`, а не
с идеальным математическим результатом. Когда `libm` сама ошибается
на больших аргументах, ULP-число растёт даже при хорошей
реализации.

## Эволюция подхода к точности

Этот раздел описывает, как менялся механизм суммирования в процессе
разработки и почему финальный выбор пал на метод Шевчука.

### Проблема: ошибки округления при суммировании рядов

Все тригонометрические, показательные и логарифмические функции
вычисляются через разложение в ряд Тейлора. Ряд для `exp`, `sin`,
`cos`, `log`, `atan` содержит от 20 до 60 слагаемых, различающихся
по величине на несколько порядков. Когда очередное слагаемое
становится на 15–20 порядков меньше суммы, его младшие биты
«уезжают» за пределы мантиссы `long double` и теряются безвозвратно.

Это классическая **потеря значимости** (loss of significance).
Ошибка накапливается как `O(n·ε)`, где `n` — число слагаемых,
`ε` — машинный эпсилон. Для `long double` с `ε ≈ 1e-19` и `n = 50`
итоговая ошибка достигает `5e-18`, что выходит за `EPS = 1e-12`
на некоторых аргументах.

### Первая версия: компенсационное суммирование по Кэхэну

Изначально применялся **алгоритм Кэхэна** (Kahan summation).
Идея: ввести дополнительную переменную `c` — компенсацию,
хранящую «хвост» от предыдущего сложения.

Реализация в виде макроса:

```c
#define S21_KAHAN_ADD(sum, c, term) \
  do {                              \
    long double _y = (term) - (c);  \
    long double _t = (sum) + _y;    \
    (c) = (_t - (sum)) - _y;        \
    (sum) = _t;                     \
  } while (0)
```

**Свойства Кэхэна:**

- Снижает ошибку суммирования с `O(n·ε)` до `O(ε)`.
- `O(1)` дополнительной памяти.
- ~4 операции вместо 1 (в 3–4 раза медленнее обычного сложения).
- Даёт **приближённый** результат с малой ошибкой.

Применялся во всех пяти функциях с рядами (`exp`, `log`, `sin`,
`cos`, `atan`) и позволял проходить тесты с `EPS = 1e-12`.
Промежуточная версия содержала `S21_KAHAN_ADD` в `s21_math.c`.

### Вторая версия: метод Шевчука (double-double)

После изучения альтернатив был выбран **метод Шевчука** в форме
расширения из 2 компонент. Идея: вместо одного числа `long double`
хранить **два** — `hi` и `lo`, сумма которых математически точно
равна результату. Подход называется **double-double**.

```c
typedef struct {
  long double hi;   // старшая компонента
  long double lo;   // младшая компонента (потерянные биты)
} s21_dd;
```

**Ключевые операции:**

- **`s21_two_sum(a, b, *s, *err)`** — точное сложение двух чисел.
  Возвращает `s` и `err` такие, что `s + err == a + b`
  **математически**. Это классический алгоритм 2Sum из работы
  Knuth / Møller.
- **`s21_dd_add(a, b)`** — сложение двух dd-чисел. Складывает
  старшие компоненты через `2Sum`, добавляет младшие, затем
  **ре-нормализует** результат: применяет `2Sum` ещё раз, чтобы
  гарантировать `|hi| >= |lo|` и чтобы компоненты не перекрывались
  по битам.
- **`s21_dd_ldexp(a, n)`** — точное умножение dd на `2^n`.
  Поскольку умножение на степень двойки — точная операция в
  IEEE 754, обе компоненты просто масштабируются.
- **`s21_dd_value(a)`** — сборка dd в одно `long double` через
  `hi + lo`.

**Свойства Шевчука (dd):**

- Точность: `O(ε²)` вместо `O(ε)` у Кэхэна. Для 80-битного
  `long double` с `ε ≈ 1e-19` это даёт эффективную точность
  порядка `1e-38`.
- ~6 операций на сложение (в 1.5 раза медленнее Кэхэна).
- 2 × `sizeof(long double)` на каждое число.
- Даёт **точно округлённый** результат, независимый от порядка
  суммирования.

Метод назван в честь **Джонатана Шевчука** (Jonathan Richard
Shewchuk, UC Berkeley), опубликовавшего работу *«Adaptive
Precision Floating-Point Arithmetic and Fast Robust Geometric
Predicates»* в 1996 году. Изначально алгоритм применялся в
вычислительной геометрии для гарантированно точных предикатов
ориентации, а также используется в `math.fsum()` в Python.

### Третья версия: FMA-based range reduction для exp

Отдельная оптимизация для `s21_exp`: range reduction
`r = y − k·ln2` через FMA. Это позволяет сохранить младшие биты,
которые теряются при обычном умножении `k * LN2_HI`.

**Проблема:** для `y = 100`, `k = 144`. Произведение `k·LN2_HI`
вычисляется с округлением до `long double` — младший бит теряется.
Затем это произведение вычитается из `y`, и ошибка остаётся в `r`,
откуда переходит в `exp(r)`.

**Решение:** FMA (`fused multiply-add`) вычисляет `k·LN2_HI` и
остаток от округления **одной операцией** — точно. Результат
раскладывается на две компоненты, которые потом вычитаются
через `dd_add`:

```c
long double khi = (long double)k * S21_LN2_HI;
long double khi_err = __builtin_fmal((long double)k, S21_LN2_HI, -khi);
```

**Результат:** ошибка `exp` на больших аргументах упала в 2–3 раза:

| x | Было | Стало |
|---|---|---|
| 5.0 | 2.78e-17 | 1.39e-17 |
| 10.0 | 7.11e-15 | 3.55e-15 |
| 20.0 | 2.62e-10 | 1.75e-10 |
| 100.0 | 1.38e+26 | 4.35e+25 |

**Ограничение:** FMA доступна только для 80-битного `long double`.
Для 128-битного формата x87 не поддерживает FMA, поэтому там
используется обычное разбитое вычитание — точности и так хватает
(`exp` совпадает с `libm` побитово).

### Четвёртая версия: FMA для sin/cos (неудачная гипотеза)

После успеха с `exp` была предпринята попытка применить тот же
приём к `sin`/`cos` — сделать FMA-based range reduction по модулю
`2π`. Гипотеза: `n * 2π_hi` теряет младшие биты при округлении,
и FMA это исправит.

**Результат на малых аргументах:** улучшения не последовало.
Таблица отклонений от `libm` осталась идентичной до последней цифры:

| x | v4 (без FMA) | v5 (с FMA) |
|---|---|---|
| `sin(10)` | 1.95e-16 | 1.95e-16 |
| `sin(20)` | 2.84e-16 | 2.84e-16 |
| `sin(100)` | 3.00e-15 | 3.00e-15 |
| `cos(10)` | 1.26e-16 | 1.26e-16 |
| `cos(100)` | 1.76e-15 | 1.76e-15 |

**Причина:** узкое место в `sin`/`cos` — не range reduction,
а накопление погрешности при вычислении слагаемых ряда Тейлора
(`term *= -x2 / (i*(i-1))`). За ~20 итераций ошибка накапливается
до `1e-15…1e-16`, и она доминирует над ошибкой приведения
аргумента. FMA улучшает только последний шаг, но не влияет
на уже накопленную погрешность.

В `exp` эффект есть, потому что там `r` вычисляется один раз
и напрямую определяет точность результата.

**Дополнительная проверка с большими аргументами** (1e3, 1e6, 1e10):
предполагалось, что на больших `x` range reduction теряет точность
сильнее, и FMA даст эффект. Гипотеза не подтвердилась — таблица
отклонений совпадает с точностью до последнего знака:

| x | sin без FMA | sin с FMA | cos без FMA | cos с FMA |
|---|---|---|---|---|
| `1e3` | 2.08e-14 | 2.07e-14 | 3.05e-14 | 3.05e-14 |
| `1e6` | 3.46e-11 | 3.46e-11 | 1.29e-11 | 1.29e-11 |
| `1e10` | 3.22e-07 | 3.22e-07 | 1.80e-07 | 1.80e-07 |

**Фундаментальная причина:** на больших аргументах ошибка `sin`/`cos`
определяется не точностью `n * 2π`, а самим фактом, что `n = x/(2π)`
слишком велико для `long double`. Даже если вычислить `n * 2π`
идеально, остаток `r = x − n·2π` может быть точно представлен
лишь до `ε · |x|`. Для `x = 1e10` это `1e-9`, что даёт ошибку
`sin` порядка `1e-7`. Это **argument reduction problem** — известная
проблема тригонометрии с плавающей точкой, решаемая только арифметикой
произвольной точности (MPFR и аналоги).

**Что показал 128-битный режим:** при переходе на quad precision
33 значащих цифр достаточно, чтобы `n = x/(2π)` не теряло точность
при извлечении остатка `r`. В результате `sin(1e10)` и `cos(1e10)`
дают **0 ULP** в 128-битном режиме — argument reduction problem
полностью исчезает. Это подтверждает, что проблема была именно
в точности представления `n`, а не в алгоритме.

Негативный результат для 80-битного режима сохранён в ветке
`v5-fma-trig` для истории.

### Пятая версия: ULP-метрика

Дополнительно к абсолютным отклонениям `|libm - s21_*|` добавлена
**ULP-метрика** — нормированная оценка точности в единицах младшего
разряда. Это позволяет сравнивать точность разных функций между
собой и понимать, где мы находимся относительно предела
представимости.

Реализация — хелпер `s21_ulp_diff` в `test.c`:

```c
static long double s21_ulp_diff(long double got, long double expected) {
  if (got == expected) return 0.0L;
  if (got != got || expected != expected) return got - expected;
  long double ulp = nextafterl(expected, INFINITY) - expected;
  if (ulp <= 0.0L || ulp != ulp) {
    ulp = expected - nextafterl(expected, -INFINITY);
  }
  if (ulp <= 0.0L || ulp != ulp) return fabsl(got - expected);
  return fabsl(got - expected) / ulp;
}
```

**Что показала ULP-таблица (80-бит):**

- **`log`** — 0–1 ULP везде, включая `1e10`. Double-double работает
  идеально.
- **`exp`** — 0–2 ULP на малых `x`, растёт до 247 ULP на `1000`.
  Относительная точность при этом остаётся на уровне `ε`.
- **`atan`** — 200–350 ULP на малых `x` при абсолютной ошибке
  `~1e-17`. То есть мы уже на пределе представимости.
- **`sin`/`cos`** — до `1e13 ULP` на `1e10`, но это ограничение
  не нашего кода, а самого `long double` (argument reduction
  problem).

**В 128-битном режиме** все функции дают **0 ULP** на всём
диапазоне, включая `sin(1e10)` и `cos(1e10)`. Это доказывает,
что алгоритмы корректны, а ограничения 80-битного режима —
фундаментальные, а не программные.

Ветка: `v6-ulp-report`.

### Сравнение подходов

| Метод | Ошибка суммирования | Стоимость итерации | Память на число |
|---|---|---|---|
| Обычное сложение | `O(n·ε)` | 1 операция | 1 × `long double` |
| Кэхэн | `O(ε)` | ~4 операции | 2 × `long double` |
| Шевчук (dd) | `O(ε²)` | ~6 операций | 2 × `long double` |
| Шевчук + FMA (exp) | `O(ε²)` + точный range reduction | ~6 операций | 2 × `long double` |

### Почему выбор пал на Шевчука

1. **Точность выше.** На `exp`, `log`, `atan` выигрыш 2–3 порядка.
2. **Независимость от порядка суммирования.**
3. **Совместимость с разбитыми константами.** `2π = HI + LO`
   и `ln2 = HI + LO` естественно встраиваются в dd-арифметику.
4. **Стоимость приемлема.** Разница в 1.5 раза с Кэхэном
   несущественна.

### Где выигрыш ограничен

Основная ошибка накапливается не в самой операции сложения,
а в вычислении слагаемых (`term *= -x2 / (i*(i-1))`). Каждое
умножение и деление вносит свою погрешность `~ε`, и она доминирует
над ошибкой суммирования. Шевчук убирает вторую составляющую,
но не первую.

Там, где Шевчук раскрывается:

- **`s21_log`**: финальная сборка `2·sum + count·ln2_hi + count·ln2_lo` —
  три слагаемых сильно разного порядка.
- **`s21_exp`**: FMA-based range reduction + `s21_dd_ldexp(sum, k)`
  перед делением `1/result`.
- **`s21_atan`**: точное вычитание `π/2 − sum` для `x > 1`.

Там, где выигрыш минимален:

- **`s21_sin`/`s21_cos`**: слагаемые ряда убывают монотонно,
  доминирует погрешность самих слагаемых. Попытка улучшить через
  FMA (v5) подтвердила это — и на малых, и на больших аргументах.

### Итог

Обе версии проходят все 454 теста с `EPS = 1e-12`. Финальная
версия на Шевчуке + FMA для `exp` даёт дополнительный запас
на сложных аргументах. История коммитов содержит все этапы:
`v1-kahan` → `v2-shewchuk` → `v3-128bit-ldbl` → `v4-exp-precision`
→ `v5-fma-trig` → `v6-ulp-report`.
